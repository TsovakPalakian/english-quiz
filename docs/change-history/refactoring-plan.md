### Архитектура адресов и процессов (делаем позже)

Название: **разделение по поддоменам** (subdomain split). Отдельные UI на разных адресах = микрофронтенды (не цель). Отдельные серверные процессы = микросервисы в умеренном виде. Один origin с `/chat` и `/admin` = маршрутизация по путям (сейчас так; контроль процессов слабее).

- [ ] 85. Цель: **три публичных адреса** на одном родительском домене:
  - `app.` — уроки, экзамены, аккаунт;
  - `chat.` — сообщения и WebSocket;
  - `api.` — общий API, если не оставлен за app/chat.
- [ ] 86. Отдельный Worker на каждый адрес: свой деплой, логи, лимиты — видно, что упало.
- [ ] 87. Связь Worker↔Worker только через **service bindings** (не публичный HTTP между собой).
- [ ] 88. Cookie сессии на родительском домене (`.…`), один вход.
- [ ] 89. Общие D1, R2 и те же Durable Objects чата; данные не копировать «на сервис».
- [ ] 90. Сначала границы в коде и этапы 30–51 / M1 / L4, **потом** физическое разбиение Worker.
- [ ] 91. Порядок выноса: после границ модулей — chat на `chat.`; затем при необходимости выделить `api.` / утончить `app.`.
- [ ] 92. При необходимости позже четвертый адрес `media.` — не раньше, чем стабильны app/chat.
