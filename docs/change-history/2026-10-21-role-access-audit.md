# Аудит ролей и доступа

Дата: 21 октября 2026. Проверяется текущее локальное дерево проекта, а не соответствие развернутой версии на сервере.

## Последующее решение

Пользователь согласовал единую review queue для всех учителей независимо от группы. В локальном модуле это реализовано отдельным этапом: [Общая очередь проверки](2026-10-21-shared-review-queue.md). Описанные ниже наблюдения сохранены как история аудита до этого решения. Для review queue назначение больше не является границей доступа, поэтому самоназначение больше не нужно для получения доступа к ней. Вопрос прав назначения и остальных областей остается отдельным; production не изменен.

## Требование

Разработчик (DEVELOPER) имеет все служебные возможности учителя (ADMIN) и дополнительные административные права. Ученик (USER) не получает служебные права. Доступ к данным дополнительно зависит от владельца, группы, состояния записи и авторства.

Старые комментарии «not imported»/«disabled candidate» в отдельных файлах не использовались как доказательство отсутствия в production: проверялась цепочка импортов.

## Фактическая матрица

| Область | Ученик USER | Учитель ADMIN | Разработчик DEVELOPER |
| --- | --- | --- | --- |
| Собственный профиль, пароль, passkeys, сессии | Свои | Свои | Свои |
| Личные материалы и прогресс | Свои | Свои и разрешенный просмотр учеников | Свои и разрешенный просмотр учеников/учителей |
| Общие уроки, определения, старые квизы, Speakout | Читать разрешенное | Создавать/редактировать; группа обычно не ограничивает | Все возможности учителя |
| Группы и назначения преподавателей | Своя доступная группа | Управление всеми группами и назначениями | Все возможности учителя |
| Student invite | Принять приглашение | Создать с назначенным в группу преподавателем | Создать; сам разработчик не обязан быть назначен |
| Teacher invite | Нет служебного создания | Создать; одобрить приглашенного им учителя | Создать; одобрить любого доступного заявителя |
| Обычная регистрация учителя без invite | Ожидание одобрения | Не может одобрить | Может одобрить |
| Экзамены/оценивание | Свое прохождение и опубликованные результаты | Подготовка/назначение; проверка назначенного экзамена | Возможности учителя, включая более широкий доступ к проверке |
| Чат | Разрешенные контакты/комнаты | Служебные действия; групповой доступ зависит от обработчика | Все служебные возможности; все группы |
| Чужие личные песни/часть библиотеки | Нет | Ограничено | Дополнительный доступ |
| Удаление чужих данных, изменение роли/активности/скрытости | Нет | Нет | Да, с проверками целевого аккаунта |
| Bugs: чтение и Resolve | Нет | Нет | Да |
| Новая review queue и история попыток | Свои предложения в уроках | Назначенные группы | Все группы |
| Настройка AI-провайдеров в изолированном реестре | Нет | Нет | Да |

В просмотренных служебных проверках не найдено отдельной операции, разрешенной ADMIN, но запрещенной DEVELOPER именно из-за меньших прав роли. Это не доказательство полного покрытия всех комбинаций данных и состояний. Роли не оформлены единой централизованной матрицей capabilities: предикаты повторяются в разных модулях.

## Обнаруженное

### 1. Высокий приоритет: самоназначение обходит границу review queue

- 🟥 Проверено: AccountGroupTeachers.save допускает любого ADMIN без проверки существующего назначения в целевую группу (src/account-group-teachers.mjs:13). Production-маршрут проверяет роль, видимость пользователей и CSRF, но не полномочие на эту группу (src/learning-integrated-worker.mjs:286).
- Локальное воспроизведение: outsider получает 403 от QuizReviewService.checkContext для группы 1; сохраняет себя в teacherIds группы 1 с актуальной ревизией; тот же checkContext после этого разрешен. Пользовательская роль не повышается до DEVELOPER, но ограничение по группе обходится.
- Требуемое решение: определить, кто вправе менять назначения. Если группы должны быть границей доступа, самоназначение не может оставаться свободным: отдельное право разработчика либо назначенного уполномоченного преподавателя. До согласования код не изменен.
- ⬜ После решения добавить регрессионную проверку всей цепочки: назначение -> invite -> чат -> review queue.

### 2. Средний приоритет: разные правила групп в старом и новом функционале

- 🟥 Проверено: StudyService.lessons дает любому ADMIN все уроки, включая неопубликованные (src/learning-study.mjs:29,143); GroupService.manage/assignStudent не проверяют назначение учителя (src/learning-groups.mjs:117,146). managedAccount разрешает учителю открыть любого активного нескрытого ученика, без связи по группе (src/worker.js:3512).
- В локальной фикстуре outsider увидел уроки [1,2,3], как разработчик; ученик увидел только [1]. Новая review queue для того же outsider группу 1 не разрешает.
- Durable chat ограничивает членство назначениями при наличии записи назначений (src/chat-worker.mjs:89), но legacy MessageService.groupAccess разрешает всем staff (src/learning-messages.mjs:60). Для групп без записи назначений durable chat также сохраняет широкий доступ учителей. Требуется учитывать реально доступные маршруты и совместимость.
- Требуемое решение: явно выбрать политику «учитель всех групп» или «учитель назначенных групп» для каждой области и согласовать исключения. Не сужать существующий доступ массово без миграционного плана.

### 3. Уточнение: неизменяемость и независимая проверка не глобальны

- 🟩 Новые квизы: запрет самоодобрения действует и для разработчика (src/quiz-review.mjs:100); SQL CHECK также запрещает reviewer_id=author_id. Утвержденную версию нельзя UPDATE/DELETE даже через обычный прямой SQL: triggers в migrations/quiz-review-draft/001_quiz_review.sql:60. Исправление идет новой версией.
- 🟩 Не всякое редактирование запрещено: черновик/возврат редактирует его автор; учитель или разработчик не переписывает чужой черновик напрямую. У одобренной версии можно предложить новую ревизию.
- 🟩 Это не универсальное правило всего приложения: например, изменение реквизитов своего аккаунта разработчик может одобрить сам; у ADMIN есть отдельный запрет (src/worker.js:3374). Старые квизы сохраняют существующий CRUD, без новой схемы approval.
- ⬜ Отдельно согласовать, нужен ли разработчику обход независимой проверки в новом модуле. Сейчас обхода нет; это правило качества и истории, а не недостаток прав роли.

## Проверка

160 успешных тестов/тестовых файлов в трех прогонах: integrated/production routes, назначения и invites, personal, экзамены, messages, review/generation/providers; локальный Cloudflare chat runtime и role navigation для USER/ADMIN/DEVELOPER; stage, реальные account handlers на фикстурах, sessions, profile, source media, embeds и перенос runtime. Первоначальный запуск chat runtime был заблокирован sandbox EPERM на loopback; повтор с разрешенным локальным сервером прошел. Ошибок приложения этими прогонами не обнаружено; зеленые тесты не отменяют описанный обход политики, которого они не запрещают.

Дополнительно выполнены одноразовые локальные SQLite-проверки outsider/self-assignment и списка уроков, только на synthetic in-memory fixture. Реальная БД, accounts.sqlite, секреты, сервер анализатора и production API не использовались и не изменялись. Каждый экран и каждый маршрут со всеми комбинациями ролей/владельцев не проверялись вручную; полный security pentest не заявляется.
