# План скорости, стабильности и рефакторинга

Дата среза: 2026-10-18. Полевых LCP, INP, CLS, TTFB и FCP нет. Цифры ниже сняты с локальной production-сборки `rollback/production-assets` и исходников.

Связанный список этапов 1–51 и договоренности 52–102 (процесс, стек, subdomain split app/chat/api): [план рефакторинга](refactoring-plan.md). Этот файл задает выбранную практику и порядок работ по скорости и долгосрочному рефакторингу.

## Выбранная практика

**Vite + поэкранные острова на Preact.** Весь сайт сразу на React или Vue не переписываем.

Почему так:

- Первый экран тормозит размер JS и HTML, а не отсутствие фреймворка. `preview.js` ~1,2 MB (gzip ~282 KB), HTML ~163 KB (76 секций, ~420 кнопок).
- Connecting чата упирается в Worker и Durable Object. Новый UI-слой это не ускорит.
- Preact маленький, API совместим с React, можно подключать React-библиотеки (виртуализация списков) и позже перейти на React точечно, если острова разрастутся.
- Острова: чат, длинные списки (экзамены, админка, архив) получают свой chunk и виртуальный список. Остальной учебный UI остается на текущем коде, пока его не разрежут Vite.
- Сборка: Vite (code-split, `import()`, хеш в имени файла). Существующий `ops/build-learning-production-assets.mjs` остается входной точкой деплоя, пока Vite не отдаст те же URL.

Не делаем как основной путь: одномоментный SPA на React или Vue, Socket.io поверх своего WebSocket, тяжелые UI-kit.

## Как проверять

Пока нет поля:

- Lab: Lighthouse и Coverage на одном сценарии (холодный вход ученика, урок, Messages) до и после каждого этапа.
- Сеть: waterfall, вес критической цепочки, `curl` `time_starttransfer` с 2–3 регионов.
- Чат: `performance.mark` до первого списка и до snapshot; `wrangler tail`.
- Регрессии: `npm run check`.

Когда появится beacon: p75 LCP, INP, CLS, TTFB, FCP отдельно mobile и desktop. Цели, пока нет своего бенчмарка (пороги Google «Good»): LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1, TTFB HTML p75 ≤ 0,8 с, Connecting p75 ≤ 1,5 с.

## Быстрые победы (до 1 дня)

## Среднесрок (1–4 недели)

### M1. Границы модулей, затем Vite

- Проблема: общий `let`/`const` и monkey-patch (`material-upgrades`, `exam-workflow`) не дают честный `import()`.
- Сделать: этапы 33–35 плана. Вызовы через явные функции или `window`. `staging/material-upgrades.js` перенести в `client/` или `production/`. Корневые `preview.html` / `preview.css` свести к `site/`. Затем Vite: chunk shell, cards, lessons, exams, admin, songs. Scoring и grammar вынести из `catalog-loader`.
- Эффект: первый экран заметно меньше gzip ~282 KB.
- Сложность: высокая. Риск: высокий.
- Проверка: bundle analyzer, Lighthouse до и после, `npm run check`.

### M2. Меньше DOM на старте

- Проблема: 76 секций парсятся и лежат в памяти всегда.
- Сделать: shell и текущий экран в HTML. Остальные секции подгружать при `data-jump`.
- Эффект: меньше parse и layout, лучше FCP и INP.
- Сложность: средняя или высокая. Риск: средний (ссылки, назад, скрытые кнопки).
- Проверка: число узлов DOM в Performance, LCP.

### M3. Списки

- Проблема: полный `innerHTML` на сотнях строк. `content-visibility` уже стоит, этого мало.
- Сделать: точечный DOM или виртуализация (библиотека вроде virtua) для админки, архива, экзаменов и ленты чата. Сначала один самый длинный список.
- Эффект: фильтр и скролл без длинных фризов.
- Сложность: средняя. Риск: средний.
- Проверка: Performance на списке 200+ строк, полевой INP.

### M4. Чат: сервер и кэш списка

- Проблема: Connecting и пустой список до snapshot.
- Сделать: этапы 38–40 и 44. Не вызывать migrate `/status` без нужды. `invalidate` не сбрасывает `roomIndex`. Быстрее снимать `policyDirtyAt`. Не смешивать тяжелый `policy` и `/profiles` на одном объекте без очереди. У кэша IndexedDB — версия схемы и TTL, старый список помечать «обновляется».
- Эффект: короче Connecting, список виден сразу и не врет долго.
- Сложность: средняя. Риск: средний (устаревшие права).
- Проверка: mark Connecting, `wrangler tail`.

### M5. Worker ближе к запросу

- Проблема: cold start и TTFB. `src/worker.js` ~208 KB на пути чата. Статика тоже проходит Worker.
- Сделать: сузить импорты чата. Статику с `?v=` отдавать с CDN без лишней логики аккаунтов, не ослабляя проверки приватных API.
- Эффект: ниже TTFB `/` и handshake сокета.
- Сложность: средняя или высокая. Риск: средний.
- Проверка: startup time в логе деплоя, TTFB `/` и `/api/messages/socket`.

### M6. Ошибки и хвосты окружения

- Проблема: поломки после деплоя видны поздно. В коде остались ветки `auth/neon/`.
- Сделать: клиентский `pageerror` и 5xx Worker в один журнал. Убрать или явно изолировать neon-совместимость. Обновить `docs/storage.md` и `docs/chat-management.md`.
- Эффект: короче время до обнаружения поломки, меньше мертвых веток.
- Сложность: средняя. Риск: низкий.
- Проверка: доля сессий с JS error, доля 5xx.

### M7. Острова Preact на двух экранах

- Проблема: чат и длинные списки дороже всего по INP, а монолитный `innerHTML` плохо режется.
- Сделать: после M1 завести Vite-остров Preact для Messages и для одного списка (экзамены или админка). Общий shell, роутер сайта по-прежнему открывает секцию. Состояние чата (сокет, snapshot, IndexedDB) оставить в модуле, UI рисует Preact.
- Эффект: предсказуемые обновления и свой маленький chunk.
- Сложность: высокая. Риск: высокий (два способа рисовать UI).
- Проверка: INP этих экранов, размер chunk, сценарии отправки сообщения и фильтра списка, CSP `script-src 'self'`.

## Долгий рефакторинг (больше месяца)

Порядок обязательный: B → M1 → M2/M4 → M7. Полный перенос UI только после того, как острова и chunk доказали, что первый экран и INP лучше lab-базы.

### L1. Все горячие экраны островами

- Экраны: чат, экзамены, админка, архив, карточки с длинной сеткой.
- Каждый остров: свой вход Vite, виртуальный список где строк много, тесты на поведение, не на снимок верстки.
- Учебные редкие экраны остаются на текущем JS, пока их не трогают по продукту.

### L2. Единый клиентский слой данных

- Сейчас `localStorage`, `sessionStorage`, IndexedDB и `ContentCache` размазаны (хвост этапа 15, этап 36).
- Один модуль: ключ, версия, TTL, подписка. Preact-острова читают его, старый UI тоже.
- Эффект: нет рассинхрона кэша чата, каталогов и черновиков.

### L3. Роутинг по экранам

- Вместо одного HTML на 76 секций: URL или тот же `data-jump`, но документ собирается из shell + экран.
- История назад и глубокие ссылки сохраняются.
- Эффект: DOM и JS пропорциональны открытому разделу.

### L4. Серверные границы

- Чат: реестр комнат как источник прав, без полного обхода ящиков.
- Accounts: `worker.js` перестает быть монолитом на каждом маршруте.
- Study: сузить `legacy_*` и `entity_id_legacy` до того, что еще нужно для файлов R2 (этап 50).
- Наблюдаемость: SLO из раздела «Как проверять», синтетика из 2–3 регионов.

### L5. Когда имеет смысл React целиком

Только если острова Preact уже покрывают большую часть UI и команде нужен один рантайм. Тогда Preact-острова переводятся на React точечно (API близкий). Новый продукт с нуля на React не начинаем, пока M1–M5 не закрыты: иначе перенос 1,2 MB императивного кода не улучшит TTFB и Durable Object.

Vue как основной UI не выбираем: отдельная модель, нет выигрыша относительно Preact для островов внутри текущего сайта.

### L6. Медиа уроков

- Картинки с размерами, `loading=lazy`, современный формат где есть исходник.
- PDF и HEIC остаются по запросу.
- Эффект: LCP урока, не главной.

### L7. Уборка репозитория

- `chat-icons.full.js` (~358 KB): сборка из пакета `lucide` в CI, полный бандл не хранить как обычный исходник.
- Судьба `rollback/` (pdfjs-runtime, старые ассеты) и корневых Python-утилит: архив вне репо или явная пометка «оставить».
- Тесты: `UI_BOOT_EXAM_FLOWS` с уровнями групп; по возможности автоматизировать `test-settings-production-ui`.
