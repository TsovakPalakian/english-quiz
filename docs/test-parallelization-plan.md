# План ускорения и распараллеливания тестов проекта

## 1. Анализ текущего состояния тест-раннера `ops/check-all.mjs`

### 1.1. Текущая структура выполнения
- В проекте **165 тестов** (164 тестовых скрипта в `test/` + Vitest).
- Все тесты делятся на две категории:
  1. **Быстрые тесты (non-browser, ~115 тестов)**: юнит-тесты D1, шифрования, парсеров, API.
  2. **Браузерные тесты (Playwright Chromium, ~50 тестов)**: файлы с суффиксом `-ui.mjs` или `ui-boot`.

### 1.2. Выявленные узкие места (Bottlenecks)
1. **Строго последовательный запуск браузерных тестов (`width = 1`)**:
   - В `ops/check-all.mjs` на строке 62 задано: `await pool(scripts.filter(browser).map(job), 1);`
   - Из-за этого ~50 браузерных тестов запускаются строго по одному.
   - Суммарное время браузерных тестов составляет более **300 секунд (5 минут)**, что составляет **90% всего времени тестирования**!
2. **Низкий параллелизм быстрых тестов (4 потока)**:
   - На современных многоядерных машинах (например, Apple M1 Pro с 10 ядрами) 4 потока задействуют меньше половины доступных ресурсов.
3. **Алфавитный порядок запуска (FIFO) вместо LPT (Longest Processing Time First)**:
   - Самый долгий тест `test-chat-ui.mjs` (48 секунд) и `test-ui-boot.mjs` (15 секунд) запускаются поздно, создавая эффект "длинного хвоста", когда все остальные потоки уже завершили работу и простаивают.

### 1.3. Проверка безопасности параллелизации браузеров
- Проведенный аудит показал:
  - Все UI-тесты запускают локальный сервер на порту `0` (`server.listen(0, '127.0.0.1')`) — ОС динамически выделяет свободные порты, коллизий портов нет.
  - Все временные каталоги создаются через `mkdtempSync` с уникальными префиксами в системном tmp, файловых конфликтов нет.
  - Тестовый параллельный запуск 3 тяжелых браузерных тестов (`test-auth-studio-ui`, `test-chat-recording-ui`, `test-constellation-return-pause-ui`) прошел за **25.9 секунды** вместо 55 секунд со 100% успехом.

## 2. Предлагаемое решение

1. **Конфигурируемый параллельный пул для браузерных тестов**:
   - Ввести переменную окружения и параметр `CHECK_BROWSER_PARALLEL`.
   - По умолчанию: `3` потока локально (или расчет от `os.cpus()`, например `Math.min(4, Math.max(1, Math.floor(os.cpus().length / 3)))`), и `2` в CI.
2. **Адаптивный параллелизм для быстрых тестов**:
   - Увеличить дефолтный `CHECK_PARALLEL` локально с `4` до `Math.min(8, os.cpus().length || 4)`.
3. **Оптимизация очереди планировщика (LPT Scheduling)**:
   - Запускать наиболее длительные браузерные тесты (`test-chat-ui.mjs`, `test-auth-studio-ui.mjs`, `test-constellation-return-pause-ui.mjs`, `test-ui-boot.mjs`) первыми в пуле, чтобы короткие тесты равномерно заполняли параллельные слоты.
4. **Сохранение полной обратной совместимости**:
   - Возможность переопределить параллелизм через переменные окружения `CHECK_PARALLEL=1 CHECK_BROWSER_PARALLEL=1` при необходимости однопоточной отладки.
