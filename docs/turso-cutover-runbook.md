## 2. Условия допуска — до изменения production

1. Получить отдельное разрешение владельца на рабочее переключение и выбрать
   короткое окно обслуживания. Никакие команды deployment здесь не запускаются.
2. Выделить отдельную production Turso и отдельный write-media bucket; тестовая
   Turso не должна становиться рабочей. Секреты только через Worker secrets,
   не чат/репозиторий. Тарифные лимиты сервисов снятием нашего лимита не исчезают.
3. Подготовить production-конфигурацию и сборку. Сейчас runtime/CLI/assets
   намеренно TEST-only: host guards, test.vars guards, TEST banner, фиксированный
   TEST_MEDIA_BUCKET. Нельзя просто заменить hostname или имя Worker в
   staging/wrangler.integrated.toml. Нужны явно разделённые production/test
   конфигурации и регрессия auth/Origin/owner/media/SQL whitelist.
4. Подготовить импорт candidate-manifest в **пустую** production-цель с
   проверкой всех строк/хешей/FK и отказом при непустой цели. ID и revisions
   не пересоздавать; исключённые профили не импортировать.
5. Перед окном обслуживания сохранить точный прежний production Worker version
   ID, конфигурацию bindings/routes и перечень имён secrets без значений.
   Проверить штатный version rollback; проверить влияние миграций DO/схем.
   Старую D1 и старые образовательные R2 JSON не удалять.
6. Заморозить учебные записи **на старом рабочем сайте**, не только TEST:
   карточки/квизы/уроки/ответы/прогресс/библиотека/медиа. Учесть открытые вкладки,
   in-flight операции и фоновые события. Запретить автоматические retries
   неизвестно завершившихся записей без mutationId/revision.
7. Выполнить свежую ограниченную source-delta и сверку frozen/deployed каталогов,
   TsovakDev ID/active/revocation и свежую копию TEST. R8 подтвердил отсутствие
   delta только на момент своего снимка. Если появились legacy изменения,
   не заменять ими вслепую отредактированные Turso строки: сравнить с baseline,
   решить конфликты и снова проверить candidate/restore. Чужие учебные JSON
   не читать. D1 использовать только для метаданных аккаунтов/авторизации.
8. Зафиксировать решение о 7 audit issues: сохранить quarantined данные
   приватно, не опубликовывать неоднозначный ответ и не объединять одинаковые
   word keys. Явно принять эти ограничения перед переключением.
9. Отдельно решить судьбу активных R7 аккаунтов в общей D1. Согласия на их
   деактивацию ещё нет. Исключение из импорта не отзывает доступ и не мешает
   login provisioning создать пустой профиль. Не изменять доступ молча.

R9.2 закрыл подготовку пакета и плана, а не production-запуск. Текущий статус
этих работ указан в production-чек-листе; оставшиеся условия переключения
сохраняются даже после локальной репетиции импорта.

## 3. Последовательность разрешённого переключения

1. После выполнения условий выше создать финальную копию и подписанный хешами
   кандидат в остановленном состоянии источников. Не использовать изменяемую
   тестовую БД как источник после контрольного снимка.
2. Импортировать кандидат в новую пустую цель и сравнить все 25 таблиц,
   IDs/revisions, единственное членство, медиа и foreign_key/integrity checks.
   Исходные медиа читать из прежнего R2; inline перенести в выделенный рабочий
   media bucket с проверкой SHA. Новые загрузки пишут только в новый bucket.
3. Развернуть подготовленную production-сборку сначала на закрытом/явно
   ограниченном адресе с учебной записью выключенной. Проверить существующий
   TsovakDev login, retained профиль, чтение уроков/библиотеки/медиа, приватность
   и запрет anonymous. Пароль, ID и роль аккаунта не менять.
4. В режиме read-only перевести production route на новый Worker. Проверить
   настоящие домен/CSP/Origin/cookies; при неуспехе сразу вернуться к старой
   версии, пока Turso не получила новых учебных записей.
5. Разрешить учебные записи и выполнить короткую приёмку на заранее объявленных
   одноразовых fixtures: translation Save, quiz add/edit/delete/readback,
   lesson draft/publish, text/song Save, media, logout/relogin, USER/Teacher
   boundaries, conflict/retry. Не менять реальные определения ради проверки.
6. Зафиксировать время первой записи, новые Worker/version/DB/bucket IDs и
   свежую копию. Следить за ошибками и внешними квотами без частого DB polling.

## 4. Возврат и критерии остановки

Остановить переключение при изменении ID TsovakDev/профиля, hash/FK mismatch,
неразрешённой delta, чужих данных в кандидате, неправильном media bucket,
провале auth/Origin/права/Save/readback или отсутствии проверенного restore.
Не повышать роли, не снимать защиты и не увеличивать нагрузку для обхода ошибки.

**До первой новой учебной записи:** вернуть ранее записанную production Worker
version/route штатным rollback; bindings/secrets должны соответствовать ей.
Снять временную заморозку только после проверки старого сайта. Новый candidate
и Turso сохранить для расследования, не удалять и не перезаписывать.

**После первой новой учебной записи:** выключить учебные записи нового Worker,
сохранить свежие Turso и новый media bucket, оставить read-only доступ либо
страницу обслуживания. Простой rollback на старые R2 JSON даст устаревшие
данные. Он запрещён, пока новые изменения не перенесены проверяемым
ID-based экспортом/merge. Существующий reverse export сохраняет данные,
но НЕ является разрешённым legacy live-import: 48 word-key collision groups
и quarantined ответы нельзя схлопывать. Предпочтителен исправляющий выпуск
нового Worker с теми же БД и медиа; destructive downgrade схем запрещён.

Не вести dual-write D1/R2/Turso для учебного контента. Auth остаётся в D1;
восстановление учебной БД не откатывает аккаунты/пароли/роли. В инциденте
учётные записи проверяются отдельно без восстановления исключённых клиентов.
