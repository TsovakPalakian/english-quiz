## 2. Судебно-технический анализ замечаний

### 2.1. Изоляция полного файла ключей и предотвращение утечки ответов
* **Текущее состояние в коде**:
  - [speakout/server/server.js#L671-L688](file:///Users/tsovakpalakian/PycharmProjects/english-quiz/speakout/server/server.js#L671-L688): вызов `GET /api/speakout/document?doc=keys` отдает весь 36-страничный файл `SO3_A1_SB_AK.pdf` (содержащий ключи ко всем разделам учебника) любому клиенту с ученической сессией.
  - Под именем `teacherResources` тот же файл требует роли `teacher` или `developer`, но под именем `keys` отдается без ограничений.
* **Требуемое решение**:
  - Разделение доступа: полный 36-страничный файл `SO3_A1_SB_AK.pdf` доступен исключительно через `doc=teacherResources` при подтвержденной роли преподавателя с проверкой пароля.
  - Для учащихся под именем `doc=keys` доступен изолированный документ `SO3_A1_U1_Keys.pdf`, содержащий только страницы 2–5 первого раздела (разворот страниц 2–3 для 1A и страниц 4–5 для 1D), предотвращая утечку ответов остальных разделов учебника.

### 2.2. Ликвидация доверия к произвольным токенам cookie learning_stage
* **Текущее состояние в коде**:
  - [speakout/server/server.js#L178-L194](file:///Users/tsovakpalakian/PycharmProjects/english-quiz/speakout/server/server.js#L178-L194): при наличии cookie `learning_stage` из 48 hex-символов сервер автоматически считает сессию валидной ученической сессией, даже если токен отсутствует в сессиях стенда и базы данных.
* **Требуемое решение**:
  - Полное удаление автоматического назначения сессии по произвольному 48-hex значению.
  - Аутентификация выполняется строго по записям в таблице SQLite `speakout_sessions`. Если сессия не зарегистрирована, запрос считается анонимным.

### 2.3. Исключение подделки IP-адреса через X-Forwarded-For
* **Текущее состояние в коде**:
  - [speakout/server/server.js#L72-L74](file:///Users/tsovakpalakian/PycharmProjects/english-quiz/speakout/server/server.js#L72-L74): `getClientIp` берет первое значение заголовка `x-forwarded-for`, передаваемое клиентом.
* **Требуемое решение**:
  - Использование реального сетевого адреса `req.socket?.remoteAddress` по умолчанию.
  - Заголовок `x-forwarded-for` учитывается исключительно при наличии явного флага обратного прокси `process.env.TRUST_PROXY === 'true'`.

---

### 2.4. Адаптивная установка флага Secure для cookie
* **Текущее состояние в коде**:
  - [speakout/server/server.js#L447](file:///Users/tsovakpalakian/PycharmProjects/english-quiz/speakout/server/server.js#L447): флаг `Secure` установлен принудительно, что приводит к отклонению cookie мобильными браузерами (WebKit на iPad) при прямом подключении по незашифрованному HTTP (`http://192.168.X.X:3456`).
* **Требуемое решение**:
  - Атрибут `Secure` выставляется адаптивно: только при защищенном соединении (`req.socket.encrypted`, заголовок `x-forwarded-proto === 'https'` или боевой режим `NODE_ENV === 'production'`).

---

### 2.5. Строгий оффлайн-шлюз для отображения распознанной речи
* **Текущее состояние в коде**:
  - [speakout/web/app.js#L484-L536](file:///Users/tsovakpalakian/PycharmProjects/english-quiz/speakout/web/app.js#L484-L536): распознанный текст и точность `Accuracy: N%` выводятся при работе облачного Web Speech API с подписью `Cloud Connected`.
* **Требуемое решение**:
  - В соответствии с утвержденной спецификацией распознанный текст и оценка точности отображаются рядом с эталонной фразой исключительно в том случае, если на устройстве верифицирован локальный оффлайн-движок распознавания речи, работающий без доступа к сети.
  - При отсутствии локального оффлайн-движка в интерфейсе отображается уведомление о блокировке: облачный Web Speech API не выполняет расчет точности и не подставляет текст рядом с эталоном.

### 2.6. Валидация идентификаторов уроков и дорожек при записи аудио
* **Текущее состояние в коде**:
  - [speakout/server/server.js#L559-L560](file:///Users/tsovakpalakian/PycharmProjects/english-quiz/speakout/server/server.js#L559-L560): эндпоинт `POST /api/speakout/speech/record` принимает произвольные `lessonId` и `trackId`.
* **Требуемое решение**:
  - Введение белого списка: `lessonId` строго в `['1A', '1D']`, `trackId` строго в `['1.01', '1.02', '1.03', 'VB1.01', 'VB1.04']`. Невалидные значения отклоняются со статусом `400 Bad Request`.

### 2.7. Изоляция манифеста и исключение утечки невыпущенных уроков
* **Текущее состояние в коде**:
  - [speakout/server/server.js#L365-L375](file:///Users/tsovakpalakian/PycharmProjects/english-quiz/speakout/server/server.js#L365-L375): эндпоинты `/api/speakout/manifest` и `/api/speakout/lesson/A1/1A` объединены и возвращают единый объект со всеми последующими уроками (1B, 1C, 2A, 2B), тестами и транскриптами.
* **Требуемое решение**:
  - Разделение маршрутов: `/api/speakout/lesson/A1/1A` возвращает строго данные урока 1A.
  - В маршруте `/api/speakout/manifest` исключаются блоки невыпущенных уроков (`lesson1b`, `lesson1c`, `lesson2a`, `lesson2b`, `unit1Review`, `unit1Test`), удаляются списки `workbookAudio`, и удаляются поля `transcript` из публичной выдачи.

### 2.8. Валидация и ограничение объема данных прогресса
* **Текущее состояние в коде**:
  - [speakout/server/server.js#L488, 505](file:///Users/tsovakpalakian/PycharmProjects/english-quiz/speakout/server/server.js#L488): лимит тела запроса составляет 1 МБ, номер страницы не проверяется на диапазон, массив `completedSteps` сохраняется без валидации.
* **Требуемое решение**:
  - Снижение лимита тела запроса прогресса до 8 КБ (8192 байт).
  - Проверка номера страницы: строго целое число в диапазоне от 1 до 177.
  - Проверка массива `completedSteps`: не более 20 элементов, длина каждой строки не более 50 символов.
  - Проверка `lessonId`: строго `['1A', '1D']`.

### 2.9. Очистка устаревших записей в таблице лимита сессий
* **Текущее состояние в коде**:

* **Требуемое решение**:

  - Ограничение максимального размера карты до 500 записей.

### 2.10. Защита сравнения пароля преподавателя от атак по времени
* **Текущее состояние в коде**:
  - [speakout/server/server.js#L416](file:///Users/tsovakpalakian/PycharmProjects/english-quiz/speakout/server/server.js#L416): проверка пароля выполняется через оператор `!==`.
* **Требуемое решение**:
  - Применение функции постоянного сравнения `crypto.timingSafeEqual` над SHA-256 хешами пароля, исключающее утечку информации по времени ответа.
