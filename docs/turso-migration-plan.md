## Важные особенности текущего кода

- Идентичность карточки часто определяется словом `en`/`base`. Совпадение слова
  не доказывает совпадение значения. Объединять только доказанно одинаковые
  определения; сохранять происхождение и соответствие старых ключей новым ID.
- Квизы сейчас привязаны к слову, а не к отдельной карточке. Сохраняем одну
  коллекцию для таких карточек. Старые хеш-ID зависят от позиции/содержимого;
  импорт закрепляет новые постоянные ID и проверяет коллизии старых.
- Связанные аккаунты сейчас совместно используют и прогресс. Нельзя при переносе
  незаметно разделить его. Обычные аккаунты получают отдельные профили.
- R2-снимки, sidecar-файлы и данные пары могут расходиться. Не выбирать источник
  по принципу «непустой побеждает»: это может воскресить удалённые данные.
- В клиенте есть слияние локальных данных и серверных массивов, отправка всего
  урока, скрытие некоторых ошибок и непостоянная очередь. Замена хранилища сама
  по себе не исправит эти пути. Нужны серверная версия, надёжная очередь мутаций
  и подтверждение сохранения только после успешного ответа.
- В нескольких R2-путях ещё используется `httpEtag` для условных записей.
  Проверить формат условного ETag отдельно; причина production-ошибок этим
  аудитом не доказана.

## Контракт новой записи

Минимальные операции: `PATCH card/{id}` с изменёнными полями,
`DELETE quiz/{id}`, `POST quiz` и операции над одним блоком/прогрессом.
Запрос содержит `expectedRevision` и постоянный `mutationId`.
В одной транзакции меняются нужные строки и сохраняется небольшое подтверждение
операции. Повтор с тем же ID и телом возвращает подтверждение без повторной
записи; тот же ID с другим телом отклоняется. Конфликт версии — HTTP 409.

Удаление использует `deleted_at`, обновляет revision сущности и родительской
коллекции/урока при необходимости. Клиент не сливает старое состояние поверх
серверного. Пример точечного обновления:

```sql
UPDATE cards SET ru = ?, revision = revision + 1, updated_at = unixepoch()
WHERE id = ? AND revision = ? AND deleted_at IS NULL;
```

Общие карточки/квизы изменяют только существующие ADMIN/DEVELOPER по проверке
сервера; управление личным материалом ученика сохраняет текущие ограничения.
Membership в учебном профиле не даёт права редактировать общие определения.
Worker проверяет доступ к карточке/профилю при каждой операции: внешние ключи
не заменяют авторизацию. Гостевые каталоги не раскрывают личный контент.
Все SQL-параметры привязанные; секрет Turso хранится только в Worker Secrets.

## Порядок переноса

1. Создать отдельную staging-БД. Применить `001_content_schema.sql` один раз;
   учёт версий не допускает повторного применения. Production-флаги выключены.
2. Сделать ограниченный read-only экспорт актуальных R2-объектов и ID аккаунтов
   D1, с манифестом ключей, ETag, размером и SHA-256. Снимки держать **вне
   директории публикуемых assets**; не вносить токены/личные данные в Git.
3. Составить отчёт расхождений: общие данные, pair-состояние, sidecar-файлы,
   удаления и локальные несохранённые изменения. Не угадывать утраченную
   историю. Разрешить неоднозначности до импорта. Для legacy `response`
   отдельно установить владельца; неоднозначные ответы не публиковать.
4. Импортировать в staging транзакционными пакетами, закрепить ID и ссылки.
   Сравнить количества, нормализованные хеши, медиа-ссылки, права и прогресс.
   Повторный импорт того же снимка не создаёт дубликатов.
5. Добавить серверный адаптер Turso, точечные endpoints и очередь клиента.
   Сначала staging; при необходимости — ограниченные сравнительные чтения.
   Не делать постоянные двойные записи без механизма восстановления.
6. На переключении временно остановить учебные записи, снять финальную дельту,
   сверить её, одновременно переключить учебные чтения и записи. Авторизация
   остаётся доступной. Старые клиенты не должны продолжать писать в R2:
   совместимые старые endpoints тоже маршрутизируются через новый адаптер.
7. Проверить сохранение после перезагрузки и из другого аккаунта. Сохранить
   старое хранилище без удаления до проверки резервного копирования/отката.

После новых записей в Turso откат — не простое выключение флага: сначала
остановить записи и перенести изменения обратно в совместимый R2-снимок.
Иначе потеряются изменения после переключения. Обратный экспорт входит в
реализацию и проверяется в staging до production-переключения.

## Проверки и ресурсы

Локальная проверка схемы: `python3 scripts/check_turso_schema.py`.
Она не подключается ни к D1, ни к R2, ни к Turso.
Подготовка staging: `node scripts/turso-staging.mjs check|init|verify`
(выбрать одну команду). `check` только читает структуру. `init` создаёт схему
только в пустой БД, проверяя пустоту также внутри транзакции; существующая
совпадающая схема не пересоздаётся. `verify` и `init` запускают тесты с ROLLBACK.
Скрипт допускает только БД `english-quiz-test` на домене Turso, читает секреты
из `.dev.vars`, не выводит их и не делает автоматических сетевых повторов.
Таблицы/индексы сверяются с локальным SQL. Не заменяет интеграционные тесты
приложения; права пользователей пока проверены только в существующем коде.
До production нужны интеграционные проверки: teacher/dev и отказ ученику;
редактирование перевода; добавление/удаление квиза; повтор запроса; конфликт
двух редакторов; перезагрузка и второй аккаунт; изоляция личных данных;
общий прогресс пары; видимость уроков; ответы заданий; существующие медиа.

Читать по индексам и страницами, загружать один урок/карточку, кешировать общие
определения по версии. Без частого polling и полной выгрузки всего каталога.
Прогресс отправлять ограниченными пакетами; срок хранения receipts ограничить.
Локальные размеры исходников не дают точный размер production-БД: фактические
байты и число строк измеряются после импорта и учитывают индексы/JSON.

## Что пока не сделано

Есть проверенный снимок, пакетный импортер, аудит неоднозначностей и сверка
строк тестовой БД, локальные UI 8788/8789 и точечный протокол карточек/квизов.
Нет обратного экспортера, опубликованного тестового Worker и переноса всех
остальных учебных мутаций. Неоднозначные ответы/прогресс сохранены отдельно;
замечания и медиа-ссылки ещё требуется разрешить до production-переноса.
URL и токен staging-БД настроены локально в `.dev.vars`, файл исключён из Git
и публикации assets. На этапе подключения отдельного staging-Worker токен
перенести в его Worker Secrets; production-Worker пока не менять.
В текущем `wrangler.toml` также задан секрет сессий открытым текстом:
перенести его в Worker Secrets отдельным контролируемым изменением;
смена значения завершит существующие сессии, поэтому сейчас не выполнена.

Официальная интеграция Workers использует `@libsql/client/web`:
[Cloudflare: Turso](https://developers.cloudflare.com/workers/databases/third-party-integrations/turso/),
[libSQL TypeScript client](https://tursodatabase.github.io/libsql-client-ts/).
