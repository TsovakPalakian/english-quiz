# Черновая схема проверки квизов

Только для отдельной локальной тестовой базы после существующей learning-схемы. **Не применять к production и не включать в migrations/learning без отдельного согласования.** Автоматического применения нет.

Реализация: `src/quiz-review.mjs`, проверка содержимого: `src/quiz-review-content.mjs`.

Проверка: `node --test test/test-quiz-review.mjs`. Каждый тест создаёт отдельную SQLite-базу в памяти. Тест D1 использует существующий D1StudyClient поверх SQLite-совместимой тестовой привязки: проверяет компиляцию и транзакции, но не означает проверку на реальном Cloudflare D1.

## Контракт

- Сервис получает actor только из доверенной аутентификации. В production подключения нет; локальный пилот использует только синтетические аккаунты.
- Создание значения и явная привязка карточки к значению доступны разработчику. Привязка не выполняется автоматически по одному написанию слова.
- Предложение создаётся только для общей карточки из слова доступного урока в выбранной группе. Учитель должен быть назначен на эту группу; разработчик имеет доступ к активным группам.
- Автор редактирует только draft/returned. Submitted нельзя править: проверяющий возвращает его с комментарием. Это более консервативное ограничение, чем действие Edit draft в демонстрационном UI; при подключении UI их нужно согласовать.
- Отправка, возврат и одобрение проверяют expectedRevision и сохраняют события с копией содержания. Повтор mutationId воспроизводит квитанцию, а другой запрос с тем же ID отклоняется.
- Глобальное одобрение по умолчанию выключено. В тестах включается через allowGlobalApproval; в будущих маршрутах настройка должна поступать только от сервера. Три пункта проверки обязательны. Самоодобрение запрещено.
- Одобренная версия неизменяема, включая SQL UPDATE/DELETE. История событий неизменяема. Исправление создаёт отдельный черновик; новая версия не наследует отметку одобрения.
- Новая версия содержит собственное авторство. Автор исходного шаблона сохраняется в истории и общей выдаче как originalAuthor.
- Общая выдача содержит последнюю одобренную версию каждой семьи, но не скрытые черновики. Несколько квизов одного типа имеют разные familyId. Старые одобренные версии сохраняются.
- Доступ через личную карточку требует явной связи с тем же значением и права читать эту карточку. Общая выдача не раскрывает идентификаторы аккаунтов, исходных уроков, комментарии и внутреннюю историю.
- Даты возвращаются без времени, в формате YYYY-MM-DD, по Asia/Yerevan.

## Локальный HTTP/UI-пилот

Запуск: `node ops/preview-quiz-review-backend.mjs`. Сервер выводит отдельный loopback-URL. Проверка: `node --test test/test-quiz-review-local.mjs` (требуются локальные Chrome и Playwright).

Пилот использует синтетические данные `test/quiz-review-fixture.mjs` и SQLite в памяти. Сохранения переживают обновление страницы и сбрасываются при перезапуске сервера. Все записи проходят через QuizReviewService. Исходный чисто визуальный макет не меняется.

Выбор тестового аккаунта не является аутентификацией. Этот сервер нельзя публиковать: он намеренно позволяет выбрать любого синтетического пользователя, включая разработчика. Он слушает только 127.0.0.1, проверяет Host и Origin записей, использует HttpOnly/SameSite-cookie, лимит тела и фиксированный список статических файлов. Реальных аккаунтов и секретов здесь нет.

Редактор пилота поддерживает все 17 типов, несколько items, пары Match/Memory, несколько правильных ответов Select all и редактируемые варианты с индексами правильных ответов. Изменение типа сохраняет локальный несохранённый черновик каждого типа; тип существующего квиза менять нельзя. Сервер проверяет структуру и возвращает ошибку в открытой форме. Отображается статический предпросмотр для проверки учителем, не полноценный проигрыватель всех учебных упражнений. Listen сохраняет слово для произношения; создание или проверка аудио в этом этапе не реализуется.

Проверки редактора: `node --test test/test-quiz-review-editor.mjs` и `node --test test/test-quiz-review-editor-ui.mjs test/test-quiz-review-local.mjs`. Почта, генерация и HTTP-маршруты production не подключены. Публичные маршруты с настоящими сессиями, лимитами и CSRF требуют отдельной реализации и проверки.

## Локальная очередь подготовки

Черновая схема `002_generation_jobs.sql` применяется только к локальному пилоту. `src/quiz-generation.mjs` реализует задачи по исходной группе/уроку, карточке, значению и типу; lease, timeout, три автоматические попытки и максимум два ручных перезапуска. Доступ запросившего учителя проверяется повторно, в том числе при сохранении результата. Уже одобренные типы пропускаются, ручные версии не обновляются.

Кнопка Prepare missing types запускает только `ops/quiz-generation-local-provider.mjs`: это детерминированные тестовые данные для drizzle/bank, не AI и не интеграция со словарями. Gap намеренно падает в первой попытке; Choice намеренно выдаёт некорректные варианты и после трёх попыток требует проверки; Listen сообщает об отсутствии аудио. Типы для наборов слов получают отдельный статус без попыток генерации.

Успешный результат сохраняется как submitted с author_kind=automatic и именем Automatic generator. Он не становится общим до решения учителя. Ошибки подготовки отображаются отдельно в Review queue и не могут быть одобрены как готовые квизы.

Назначенный учитель может выбрать Create corrected draft: сервис атомарно создаёт человеческий черновик того же типа и связывает его с исходной задачей, сохраняя причину и счётчики. После этого повторная генерация этой задачи запрещена. Черновик проходит обычную отправку и проверку другим учителем; проблема остаётся активной до одобрения. Исходная история не удаляется. Это ручная замена, а не редактирование или одобрение невалидного сырого ответа генератора.

Проверки: `node --test test/test-quiz-generation.mjs` и `node --test test/test-quiz-generation-ui.mjs`. Данные переживают reload страницы, но не перезапуск тестового сервера. Устойчивость очереди проверяется на той же тестовой базе при повторном захвате lease; долговременное хранение на реальном D1 ещё не включено. Нужны отдельные общие лимиты расходов, подключение провайдера и эксплуатационный мониторинг перед production.

## Происхождение генерации

Только черновые схемы `001_quiz_review.sql` и `002_generation_jobs.sql`: добавлены nullable generation_json версии и candidate_generation_json задачи. Существующие production-миграции не изменяются и эти схемы к рабочим данным не применяются. Ранее запущенный in-memory пилот сохраняет старую схему до перезапуска; новый запуск пересоздаёт только демонстрационные данные. Для будущей постоянной БД потребуется отдельная согласованная миграция, не повторное применение CREATE TABLE.

`createRoutedQuizGenerator({providers, includeMetadata:true})` возвращает `{content,generation}`; по умолчанию сохранён прежний режим content-only для совместимости. При подготовке настоящего AI-пилота режим метаданных нужно явно включить. Старые тестовые генераторы продолжают возвращать только content; отсутствующие сведения остаются null, без выдуманного провайдера или нулевого расхода.

Generation содержит source (provider/model/version, adapterId, locale/mode/task и configurationRevision), usage с только фактически полученными счётчиками токенов, instructionVersion, generatedAt ISO UTC и contentRevision=1. Это происхождение исходного сгенерированного содержания, не доказательство отсутствия последующих правок и не отметка проверки учителем. Пользовательские даты авторства по-прежнему без времени.

Кандидат и metadata записываются вместе под lease. Версия, generation_json и append-only событие создаются одной review-транзакцией; сбой после создания восстанавливается через mutation receipt без нового inference. Метаданные версии нельзя переписать даже до одобрения (SQL-trigger). Ручные предложения их не принимают; новая человеческая ревизия получает null, а исходное происхождение остаётся у родительской версии. Детали доступны в авторизованном get/queue, но не в sharedForCard. UI отображения source/usage в этом этапе не добавлялся.

Generation версии хранит метрики принятого кандидата. История остальных попыток описана ниже; это не полный финансовый журнал. Денежную стоимость из одних токенов автоматически не вычисляем, атомарный бюджет и сверка с биллингом ещё не реализованы.

Проверка: `node --test test/test-quiz-generation-metadata.mjs test/test-workers-ai-quiz-provider.mjs test/test-quiz-generation.mjs test/test-quiz-review.mjs`. Только отдельные SQLite-fixtures и D1-компиляция на SQLite, не настоящие D1 или AI-вызовы.

## Журнал попыток подготовки

В черновую `002_generation_jobs.sql` добавлена qr_generation_attempts. Ключ — job_id/cycle/attempt; три попытки на цикл, максимум три цикла сохраняются отдельно. Создание running-записи атомарно с увеличением счётчика, до вызова генератора. Это попытка подготовки, а не доказательство реального inference: конфигурация или quota gate могут отклонить её до внешнего вызова.

Статусы: running, accepted (кандидат прошёл локальную проверку, не одобрение учителем), rejected, error, interrupted. Кандидат и accepted-запись сохраняются атомарно. При захвате истёкшей lease незавершённая запись становится interrupted; поздний старый worker не может её переписать. Повтор сохранённого кандидата и mutation receipt не создаёт фиктивную новую попытку. Завершённые записи и идентичность попытки защищены SQL-trigger, удаления нет.

`generation.attemptHistory(actor, jobId)` и локальный GET `/local/generation/:id/attempts` возвращают цикл/номер, время начала/конца, статус, безопасный код ошибки, выбранный source и валидные фактически полученные token counters. Доступ только учителю исходной группы или разработчику, с повторной проверкой назначения; учащиеся и общие карточки журнал не получают. UI просмотра журнала в этом этапе не добавлен.

Routed generator передаёт наблюдение source/usage до проверки языка и содержания, поэтому квиз с неправильным ответом не теряет известный расход. Workers AI сохраняет валидные usage из прочитанного ответа и при невалидном JSON самого задания. HTTP-ошибки без usage, обрыв, прерывание сервера или превышение размера ответа могут оставить расход неизвестным: null/отсутствующие поля не означают 0. Обрыв после отправки запроса не позволяет обещать exactly-once inference; нужна будущая сверка расходов с провайдером. Поздние наблюдения после timeout игнорируются, а не приписываются другой попытке.

Сырые запросы, ответы, аудио, токены доступа, полные тексты ошибок и сведения аккаунтов в журнал не записываются. Для старых content-only генераторов source/usage остаются неизвестными, если они не предоставили наблюдение. Таблицы создаются только в новой изолированной тестовой БД; для постоянного хранения нужна отдельная согласованная миграция.

Проверки: `node --test test/test-quiz-generation-attempts.mjs`; локальный endpoint и старый UI-путь — `node --test test/test-quiz-generation-ui.mjs`.

## Production-ограничения

Production HTTP/CSRF и лимиты запросов, реальные роли и сессии, публичные правила отображения авторства учеников, миграция старых карточек, действующий UI, фоновые задачи, генератор, отправка почты, проверки реального D1 и production. Структурная проверка всех 17 типов не гарантирует языковую правильность и не заменяет учителя. Право на глобальное одобрение и раскрытие авторства необходимо согласовать отдельно.
